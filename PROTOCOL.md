# MQTT Chat wire protocol (v1)

What another client (e.g. the desktop app) must implement to talk to the mobile app. Reference implementation: `chat_crypto.py` (run `python3 chat_crypto.py` for its self-test).

v1 replaces the old Fernet format. There's no backward compatibility: v1 clients and Fernet clients can't read each other's messages.

## Topics

For a room named `<room>` (the room field, with spaces trimmed from both ends, case-sensitive):

| Topic | Payload | Retained |
|---|---|---|
| `chat/<room>/messages` | encrypted chat message (below) | no |
| `chat/<room>/presence/<username>` | presence JSON, **not encrypted** | yes |

Presence is unchanged from before: `{"user": "<username>", "status": "online" \| "offline", "timestamp": <unix seconds float>}`. An empty retained payload clears it. Clients republish "online" every 30 s and set an "offline" Last Will.

## Chat message

Plaintext: UTF-8 JSON `{"user": "<display name>", "message": "<text>", "timestamp": <unix seconds float>}`.

Payload sent on MQTT (ASCII text):

```
base64_standard( version || nonce || ciphertext || tag )
```

| Field | Size | Value |
|---|---|---|
| version | 1 byte | `0x01` |
| nonce | 12 bytes | random, new for every message |
| ciphertext | same length as the plaintext | AES-256-GCM |
| tag | 16 bytes | GCM authentication tag (`cryptography`'s `AESGCM` adds it to the end of the ciphertext) |

- Base64 is the **standard** alphabet (`+/`) with `=` padding, not base64url.
- AAD ("additional authenticated data") = the UTF-8 bytes of the messages topic, e.g. `chat/general/messages`. A message copied into another room fails to authenticate.
- Receivers must drop the message if:
  - the base64 is invalid;
  - the payload is shorter than 29 bytes (1 + 12 + 16);
  - the version isn't `0x01`;
  - the GCM tag doesn't verify.

## Key

The key field is trimmed of spaces at both ends, then:

1. **Raw key:** if it matches `^[A-Za-z0-9_-]{43}=?$` and base64url-decodes to exactly 32 bytes, those bytes are the AES-256 key. The room name isn't used. The Generate button produces this form: `base64url(32 random bytes)`, 44 characters with a trailing `=`.
2. **Passphrase:** anything else is treated as a passphrase:
   ```
   salt = SHA-256( b"mqttchat-scrypt-v1:" + utf8(room) )
   key  = scrypt( utf8(passphrase), salt, N=32768, r=8, p=1, dklen=32 )
   ```

Keys generated by the old Fernet "Generate" button have the same shape (44-character base64url of 32 bytes), so they're used as raw keys.

## Key fingerprint

A short value two people read aloud to confirm they have the same key. It's computed over the 32-byte key *after* the key rules above (raw key, or scrypt-derived for a passphrase), so it depends on the room for passphrases:

```
fp = hex_upper( SHA-256( b"mqttchat-fp-v1:" + key32 )[:8] )   → 16 hex chars, shown as XXXX-XXXX-XXXX-XXXX
```

Test vectors:

```
key bytes 0x00..0x1f (the raw-key test vector above)  →  273B-2CAF-623A-EBA8
passphrase "hunter2", room "general"                  →  E289-0BFB-A5B3-18D3
```

## QR exchange

QR codes carry compact UTF-8 JSON. Both types show the fingerprint of the key they carry (for the room they carry). **Neither ever contains the chat username:** the receiver uses their own name.

Key only, for people already on the broker:

```json
{"type":"mqttchat-key","version":1,"room":"chatty","key":"<key or passphrase>"}
```

Full room, so a new user can join with one scan:

```json
{"type":"mqttchat-room","version":1,"host":"broker.example","port":1883,"tls":false,
 "mqtt_user":"user","mqtt_pass":"pass","room":"chatty","key":"<key or passphrase>"}
```

| Field | Type | Rule |
|---|---|---|
| `type` | string | `mqttchat-key` or `mqttchat-room`. Anything else is rejected. |
| `version` | integer | `1`. Anything else, including `true`, is rejected. |
| `room`, `key` | string | Required and non-empty. `key` uses the key rules above. |
| `host` | string | Room type only. Required and non-empty. |
| `port` | integer | Room type only. 1–65535. |
| `tls` | boolean | Room type only. This version always exports `false` and rejects `true`, because TLS isn't implemented yet. |
| `mqtt_user`, `mqtt_pass` | string | Room type only. May be empty, for anonymous brokers. |

Readers must:
- reject any payload that fails these rules;
- show the fingerprint and get confirmation before importing;
- escape scanned text before displaying it.

The QR is only ever rendered in memory and shown with screenshots blocked (Android FLAG_SECURE). It closes after 60 s.

## MQTT client ID

Each client uses a random client ID, `mqttchat-` plus 16 hex characters, generated for every connection. It's never derived from the user name or the room config. MQTT brokers disconnect an existing session when a second one connects with the same ID, and everyone who scans the same room QR has the same config.
